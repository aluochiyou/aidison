# 项目总览与产品定义

## 1. 一句话定义

Aidison 是一个面向个人使用和面试展示的通用 DIY 工程 Agent。它把模糊目标持续转化为可理解、可比较、可实施、可验证、可追溯、可局部修订的工程方案。

它的核心资产不是聊天记录或一次性长报告，而是用户在明确依据上批准的不可变 `SolutionVersion`。BOM、实施步骤、验证计划、控制台和导出文档都是该版本的投影。

## 2. 要解决的问题

典型 DIY 项目常见的问题不是“缺少一条答案”，而是：

- 需求、硬约束、偏好和未知没有被结构化；
- 模块之间的尺寸、电气、协议、软件、预算和供应兼容性没有整体检查；
- 搜索结果和模型结论无法追溯到稳定来源；
- 候选方案缺少比较依据、反证、BOM 和验证计划；
- 用户反馈后只能整份重做，无法说明哪些成果仍有效；
- 多 Agent 任务在重试、取消、崩溃和迟到结果下可能重复写入或污染方案。

Aidison 的价值在于把这些问题变成可持久化、可测试的工程语义。

## 3. 通用 DIY 方法

项目早期把这套方法称为“苏纳法”。它不是无人机专用流程，而是一条领域无关闭环：

```text
Goal
→ RequirementRevision
→ ModuleGraph
→ ResearchQuestion
→ Evidence / Counterevidence
→ Candidate
→ CompatibilityFinding
→ DecisionRequest
→ SolutionProposal
→ SolutionVersion + BOM + VerificationPlan
→ Observation
→ ImpactAnalysis
→ PatchSet
→ New SolutionVersion
```

领域差异未来只能通过来源、兼容性、验证和动作适配器进入，不能产生 `Drone*` 等核心专用实体，也不能分叉主 Graph。

## 4. 用户和首个 pilot

- 首要用户：项目拥有者本人。
- 使用环境：Windows 桌面，Docker Desktop 承载后端，浏览器访问前端。
- 首个真实 pilot：四旋翼无人机。
- pilot 的作用：验证完整闭环，而不是把产品变成无人机配置器或飞控软件。

## 5. 用户最终应获得的内容

完成一个项目后，用户应能够回答：

1. 我的目标、约束、偏好和未知分别是什么？
2. 项目被拆成哪些模块，依赖关系是什么？
3. 关键结论来自哪里，是否存在反证、版本和适用条件？
4. 有哪些路线，为什么选择当前方案？
5. 需要购买、复用、下载、制作和配置什么？
6. 应按什么顺序实施、验证和回退？
7. 新反馈使哪些模块失效，哪些结果可以继续复用？

## 6. 已经落入代码的产品不变量

1. Agent 只提交 typed Proposal 或 staged Artifact，不能直接批准或修改 canonical truth。
2. PostgreSQL Domain 是业务事实源；LangGraph checkpoint、聊天、缓存、Artifact 和可观测平台都不是。
3. `SolutionVersion` 创建后不可原地修改。
4. `unknown`、`needs_test` 和冲突必须显式存在，不能被模型补成兼容。
5. 关键 command 使用 basis、revision、幂等 receipt 和 fencing；stale 结果不能覆盖新状态。
6. 用户反馈先形成 `Observation` 和 `ImpactAnalysis`，然后只修改受影响闭包。
7. V0 禁止支付、下单和物理设备控制。

## 7. 当前 V0 已覆盖的主旅程

当前代码已经覆盖以下结构化旅程：

```text
创建 Project
→ 批准 RequirementRevision 与 Module
→ 启动 durable Research Job
→ 两个有界 child Research Job
→ Evidence / Candidate / Compatibility / Decision Proposal
→ 用户按 option_id + basis 批准 Decision
→ durable Solution Proposal
→ 用户只批准 proposal identity + basis
→ 冻结 SolutionVersion V1
→ 提交 Observation
→ durable Impact Proposal
→ 批准 Impact
→ PatchSet + SolutionVersion V2
→ 控制台显示受影响与复用模块
```

这条旅程在 fake provider、隔离 PostgreSQL、Artifact 和浏览器层已有验证；真实 Bailian + Tavily/GitHub 的完整闭环曾成功，但重复执行不稳定。

## 8. 当前明确不是产品目标的内容

- 通用聊天平台或通用多 Agent 看板；
- 公网 SaaS、多租户、组织、RBAC；
- Kubernetes、Dapr、Celery、Redis、消息总线；
- 向量数据库、图数据库和无边界“人格记忆”；
- 动态 swarm、无限递归研究和自由创建 Agent；
- 自动支付、自动退款、自动控制无人机；
- 自建搜索引擎、MCP transport、GitHub API 或文档渲染平台。

## 9. 当前项目状态的准确表述

适合的表述是：

> Aidison 已完成一个有真实领域模型、耐久任务语义、证据链、预算账本、结构化方案修订和浏览器控制台的 V0 工程骨架；核心 non-live 回归通过，真实外部闭环已有成功样本，但 provider/tool 选择的重复稳定性尚未关闭。

不应表述为“完整产品已经完成”“所有 Provider 已验证”或“全自动 DIY 已实现”。
