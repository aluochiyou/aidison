# 后续版本路线图

本路线图是条件性规划，不代表当前已授权继续开发。恢复开发时应重新核对用户目标、工作区和外部 API 状态。

## 1. V0 封口版

目标：把现有工程骨架变成可重复演示、可恢复、可讲清楚的个人 Demo。

最小范围：

1. 先封存当前 Git 现场；
2. 建立 deterministic 成功 fixture，不依赖实时 provider；
3. 只做一次有界真实四旋翼 live gate，失败就保留透明失败态；
4. 解决或明确隔离 5 条历史 Artifact 记录；
5. 完成 Module Lens 或明确从 V0 删除该验收项；
6. 用至少一个非无人机 fixture 证明核心无领域硬编码；
7. 更新 README、状态和面试演示脚本。

V0 不新增 Redis、A2A、购物、Langfuse、向量数据库或第二 runtime。

## 2. V1：完整交互控制台与辅助采购

只有 V0 稳定后再选择：

- 独立 Research/Evidence 页面；
- Module drill-down 和 Evidence Drawer；
- Artifact viewer 和确定性 Markdown 导出；
- Decision Inbox；
- 更清晰的 Solution V1→V2 语义 Diff；
- Integration Health 卡，只展示配置状态、backend、最近检查和错误码；
- `OfferSnapshot`、商品搜索和供应商比较；
- Shopify cart/checkout handoff 或其他官方接口良好的目标市场；
- 更强的跨领域 Source/Compatibility/Verification adapter。

V1 的购物只做到发现、比较、准备购物车和跳转托管 checkout，不保存支付信息，不自动下单。

## 3. V2：受控自动化

进入条件必须同时满足：

- matched-budget 评测证明动态研究策略有收益；
- 官方交易 API、个人生产权限、沙箱、地区和对账可验证；
- effect ledger、幂等、二次批准和 ambiguous reconciliation 已实现；
- 自动化失败可回滚，用户能查看完整审计记录。

可能能力包括真实 place_order/cancel/refund、Verification/Action adapter、独立 Agent 系统间的 A2A、跨项目复用经过验证的规则和有边界的硬件测试自动化。

## 4. 研究和工程能力的晋升门

任何新 Agent、工具、检索或记忆机制都必须：

1. 与现有基线使用相同 fixture 和预算；
2. 改善预先定义的质量指标；
3. 不降低证据、幂等、安全、延迟和成本门；
4. 有明确 fallback 和删除路径；
5. 不引入第二 canonical state 或第二 durable runtime。

## 5. 面试展示建议

1. 用四旋翼需求说明通用 DIY 问题；
2. 展示 Domain 与不可变 SolutionVersion；
3. 展示两个 Research child 的 Job/Attempt/JoinReceipt；
4. 展示 Tavily/GitHub → Artifact/hash → EvidenceBinding；
5. 模拟 crash/reclaim，说明为什么不会重复提交；
6. 提交 Observation，展示 affected/unaffected 和 V2 复用；
7. 最后解释哪些通用能力采购自成熟开源，哪些是 Aidison 原创。

这比堆叠更多页面、Agent 名称或中间件更能体现工程价值。

## 6. 停止条件

恢复开发后，只要出现以下任一情况，应暂停而不是扩张范围：

- 为了修 live gate 需要放宽证据或预算不变量；
- 新框架要求迁移 canonical state；
- 新模块无法在 1–2 个独立验收切片内说明价值；
- 前端功能没有真实 Domain 数据支持；
- 需要用户登录、授权、付费或执行不可逆外部操作；
- 项目规模开始掩盖个人贡献。
